# DRAFT × DRAFT

> 運命のドラフトから、自分だけのチームを作れ。

**遊ぶ → https://draftxdraft.pages.dev**

**DRAFT × DRAFT** は、実際のNPB（日本プロ野球）ドラフト史実データをもとに、
ランダムに提示される「年度 × 球団」から実在の指名選手を1人ずつ選び、
12枠のロスターを完成させるスマホファーストのWebゲームです。

第1回の**1965年から2025年まで全61年・731通りの「年度 × 球団」、4935人**を収録しています。
南海ホークス、阪急ブレーブス、西鉄ライオンズ、東映フライヤーズ、近鉄バファローズ……
いま存在しない球団も、その年に実際に名乗っていた名前で登場します。

開発者による選手の能力評価・ランキング・強さ判定は一切行いません。
選手について保持・表示するのは、ドラフト順位や実際の守備経験、獲得タイトルといった
**客観的に確認可能な事実データのみ**です。ロスターの「強さ」をどう見るかは、
プレイヤー自身の野球知識と解釈に委ねられます。

## 遊び方

1. TOP画面でゲームモードと**出題する年度の範囲**を選び、**START** を押す
   （遊ぶ前に決めるのはこの2つだけ。スクロールなしで収まります）
2. 「ドラフトする」たびに年度×球団がランダム抽選される（ルーレット演出つき）。抽選は「シャッフルバッグ」方式で、プールを一巡するまで同じ年度×球団は絶対に出ない（一巡した場合も、直前に出たものが続けて出ることはない）
3. その年・その球団が実際に指名した選手の中から1人を選ぶ
   （候補はスクロールせずに全員見える。指名が多い年は自動で2列になる）
4. 空いている12枠のうち好きな枠を選んで登録（候補カードにはドラフト時のポジションのみを表示し、配置先を制限しない）。野手（DH含む）を登録する場合は、その場で1〜9番の空いている打順から好きな番号を選べる
5. これを12枠すべて埋まるまで繰り返す
6. 完成したら打順を編集し、客観的なチーム構成・特徴タグ・実績バッジを確認してシェア（シェアカードは画像として書き出せます）

どの選手も空いている枠であればどこにでも配置できるため、配置可能な候補が0人になってゲームが詰むことはありません。

### 出題する年度を絞る

TOP画面で「全期間 / 昭和 / 平成 / 令和」を選ぶか、開始年と終了年を自分で指定できます。
選んだ範囲は localStorage に保存され、プレイ中のゲームにも記録されるので、
途中で再読み込みしても同じ範囲のまま再開します。

範囲を選ぶと「この範囲：◯◯通り（◯◯人）から出題」と目安が出ます。
12通りを下回る範囲（単年など）では、12人そろえる間にプールを一巡してしまい
同じ年度×球団が再び出ることがあるので、その旨も表示します。

### シェアカードの画像

結果画面のシェアカードは、そのままPNG画像（1080×1350）として書き出せます。
スマホでは「画像で共有」でOSの共有シートに画像を渡し、対応していない環境
（PCのブラウザなど）ではそのまま保存に回ります。「画像を保存」はどこでも使えます。
X・LINEの投稿画面は文章しか渡せないので、画像は保存してから添えてください。

画像は `html2canvas` のようなライブラリを使わず、Canvas 2D で描き直しています
（`src/shareImage.js`）。ビルド工程も外部依存も増やさずに、SNSで切られない
4:5の解像度で出すためです。配色は表示中のテーマから読むので、
ライト/ダークと選んだアクセントカラーがそのまま画像にも反映されます。

### 表示テーマ

TOP画面の **表示設定**（STARTの下、既定は閉じています）で
「端末に合わせる / ライト / ダーク」を選べます。既定は端末（OS）の設定に追従し、
選択内容は localStorage に保存されます。アクセントカラーに載る文字色は、選ばれた色の
輝度からコントラストの高い方（黒/白）を自動で選ぶため、どの色・どのテーマでも読めます。

### ゲームモード

| モード | スキップ回数 | 備考 |
| --- | --- | --- |
| NORMAL | 3回まで | 標準ルール |
| NO SKIP | 0回 | 引いたら必ず指名 |
| HARD | 1回まで | それ以外はNORMALと同じ |

## このゲームでやらないこと

- 選手の能力値（コンタクト・パワー・球速など）
- 総合力・100点満点評価・S/A/Bランク
- 選手やチームの強さランキング、優劣判定
- 「最強」「弱点なし」等、主観に基づく評価表現

代わりに、ドラフト順位・出身（高校/大学/社会人/独立リーグ）・投打・実際の守備経験・
獲得タイトルといった事実だけを見せ、「この順位でこの選手はすごい」と
プレイヤー自身が感じられる体験を目指しています。

## 技術構成

ビルドツールに依存しない、素のHTML / CSS / JavaScript（ESモジュール）で実装しています。
`vite` などのバンドラは不要で、静的ファイルを配信できる環境ならどこでも動作します。

```
draftxdraft/
├── index.html            # エントリポイント
├── src/
│   ├── main.js            # 画面遷移・アプリ全体の状態管理
│   ├── dataStore.js        # data/*.json の読み込み（fetchベース）
│   ├── state.js            # ゲーム状態のファクトリ
│   ├── modes.js             # NORMAL / NO_SKIP / HARD とモード拡張フック
│   ├── draft.js             # 年度×球団の抽選プール・候補取得
│   ├── yearRange.js         # 出題する年度の範囲（プリセットと自由指定）
│   ├── roster.js            # 12枠定義・実績ポジション表示用の判定（配置先は制限しない）
│   ├── game.js              # 抽選→指名→スキップ→終了判定のオーケストレーション
│   ├── battingOrder.js      # 打順の並び替え
│   ├── draftRound.js        # 指名順位の表記（区分名付き）の解釈
│   ├── analysis.js          # 完成ロスターの客観分析・特徴タグ生成
│   ├── history.js           # ドラフト履歴の記録
│   ├── storage.js           # localStorage 永続化（壊れたデータにも耐性）
│   ├── share.js             # シェアカード用データ・Web Share API（画像添付）
│   ├── shareImage.js        # シェアカードをPNG画像として描き出す（Canvas 2D）
│   ├── teams.js              # 球団名の年度別解決
│   └── ui/                  # 画面・コンポーネント・演出
├── styles/                 # CSS（デザイントークン / 画面別スタイル）
│   └── tokens.css           # ライト/ダーク両テーマの配色トークン
├── data/
│   ├── teams.json           # 球団マスタ（歴代の球団名を年度で解決）
│   ├── players.json         # 選手データ（能力値フィールドは持たない）
│   ├── drafts.json          # 年度×球団の実際の指名選手一覧
│   ├── achievements.json    # タイトル/表彰バッジの表示マスタ
│   └── _raw/                # Wikipediaから持ち帰った素材（生成物の入力）
└── assets/
```

ゲームロジックと選手データは完全に分離されています。新しい年度・球団・選手を
追加したい場合は `data/*.json` にエントリを追加するだけで拡張できます
（年度・球団もコードに固定せず、データから動的に抽出しています）。

`tools/` にはデータ生成用のスクリプトが入っていますが、ゲーム本体からは
参照していません。実行にNode.jsが要るのはデータを更新するときだけです。

### データについて

選手データは調査に基づく客観的事実のみを収録しています。守備経験・二刀流判定・
タイトルなど確認が取れなかった項目は `null` または空配列のままにしており、
推測で埋めていません。この実績ポジション（`fieldingPositions`/`pitcherRoles`）は
ロスターへの配置先を制限するものではないため（どの選手も空いている枠であれば
どこにでも配置できます）、候補カードには表示せず、ドラフト時のポジション
（`draftPosition`）のみを表示しています。

### データについて

| | |
| --- | --- |
| 収録年度 | 1965〜2025年（全61回） |
| 抽選プール | 731通り（年度 × 球団） |
| 選手 | 4935人 |
| 球団 | 13（消滅した近鉄バファローズを含む） |
| 現役/引退 | 判明 4883人（98.9%） |
| 投打 | 判明 2868人（58%） |
| 守備位置 | 判明 4449人（90%） |

指名順位は、同じ年に複数のドラフトが行われた年（1966年の第1次/第2次、
2005〜2007年の高校生ドラフトと大学生・社会人ドラフト）は順位が重複するため、
`高校1巡目` `大社希望入団枠` `第2次3位` のように区分名を冠して区別しています。
候補カードでは区分を小さく上段に出し、詳細を開くと正式名称が確認できます。

近鉄バファローズは2004年限りで消滅した独立の球団として扱い、
阪急ブレーブスはオリックスの前身なのでオリックスに含めています。

### データの取得と更新

`data/players.json` / `data/drafts.json` は、Wikipediaの
「YYYY年度新人選手選択会議 (日本プロ野球)」から機械的に生成しています。
手順は4段階で、Wikipediaを叩くのは1と3だけです。

1. **取得** — GitHub Actions の `fetch-drafts` ワークフローを `workflow_dispatch` で実行すると、
   ランナーが各年度のウィキテキストを取得して `data/_raw/YYYY.wikitext` としてコミットします
   （`years` に `1965-1980` のような範囲、または年度をスペース区切りで指定）。
2. **パース** — `node tools/parse-drafts.mjs` が `data/_raw/*.wikitext` を読み、
   指名順位・ドラフト時ポジション・出身校を抽出して2つのJSONへ反映します。
   既に登録済みの選手（旧字体を正規化した名前 × 年度 × 球団が一致）は
   調査済みの値を温存し、上書きしません。再実行しても結果は変わりません。
3. **記事の取得** — 同じワークフローを `fetch_status: true` で実行すると、
   各選手の記事の冒頭文とカテゴリを `data/_raw/player-intros.json` に持ち帰ります。
   取得済みの記事は読み飛ばすので、途中で落ちても続きから再開できます。
4. **判定と反映** — `node tools/classify-status.mjs` が冒頭文から現役/引退を判定し、
   `node tools/apply-player-status.mjs` が `players.json` に反映します。
   続けて `node tools/apply-player-profile.mjs` が、同じ冒頭文から
   投打（「右投左打」）と守備位置（「プロ野球選手（内野手、外野手）」）を読み取ります。
   判定規則を直したときは3を飛ばして4だけ回せます。

記事が内訳まで書いていない「内野手」「外野手」は、内訳不明のワイルドカード
（`IF` / `OF`）として持たせ、特定の守備位置には断定しません。
二刀流の印は「兼」「二刀流」と明記されている場合にだけ立てます
（投手から野手へ転向した選手を二刀流と誤って扱わないため）。

`data/_raw/` を残してあるので、判定規則を変えたときは
2〜4を回すだけで `players.json` / `drafts.json` を作り直せます。
実際、素材から作り直しても同じ内容になることを確認しています。

#### 現役/引退の判定

日本語版Wikipediaの野球選手記事は、冒頭が定型で書き分けられています。

- 「〜は、…の**元**プロ野球選手」→ 引退（「元プロ野球投手」「プロ野球元投手」等の揺れも拾う）
- `Category:存命人物` が付いていない（＝物故者）→ 引退。
  物故者の記事には「元」を付けない慣習があるため、これを見ないと
  1960年代の指名選手が「現役」になってしまう
- 「〜に所属した」「所属していた」など過去形の在籍表現 → 引退
- 野球解説者・評論家・審判員・コーチなど、現役と両立しない後職 → 引退
- 現在の所属先が書かれている → 現役

どの手がかりも無い場合は埋めません。ただしWikipediaに記事が無い選手のうち、
1994年より前に指名された選手は引退として扱っています。NPBの最年長出場記録は
50歳（山本昌・2015年）で、高校生でも指名時に18歳なので、年齢の上で現役では
あり得ないためです（推測ではなく年齢の帰結）。

それでも判別できなかった52人は `unknown` のままにしてあり、
画面には「在籍状況不明」と出ます。誤って「現役」と表示するよりよいという判断です。

## ローカルでの実行

Node.js等のビルド環境は不要です。リポジトリ直下で任意の静的サーバーを起動するだけで動きます。

```bash
python3 -m http.server 8000
```

起動後、ブラウザで `http://localhost:8000` を開いてください
（`fetch` でJSONを読み込むため、`file://` で直接開くのではなくローカルサーバー経由で開く必要があります）。

## デプロイ

ビルド不要の静的サイトなので、静的ファイルを配信できる環境ならどこでも公開できます。
ファイルの参照はすべて相対パスで、サイトのURLをコードに埋め込んでいないため、
どのドメインに置いてもそのまま動きます。

### Cloudflare Pages（推奨）

無料で、独自ドメインを買わずに `〜.pages.dev` のURLで公開できます。
リポジトリをつなぐと、`main` に push するたび自動で反映されます。

1. https://dash.cloudflare.com/ でアカウントを作る（無料）
2. **Workers & Pages** → **Create** → **Pages** タブ → **Connect to Git** から
   このリポジトリを選ぶ
3. ビルド設定は次のようにする（ビルドは走らせない）

   | 項目 | 値 |
   | --- | --- |
   | Framework preset | None |
   | Build command | （空のまま） |
   | Build output directory | `/` |

4. **Save and Deploy**

プロジェクト名がそのままURLになります（`draftxdraft` → `draftxdraft.pages.dev`）。
名前は先着なので、埋まっていたら別の名前にしてください。

`wrangler.jsonc` に `pages_build_output_dir` を書いてあるので、Cloudflare 側は
それを読んでリポジトリ直下を配信します。

`_headers` はレスポンスヘッダの設定で、Cloudflare がこれを読んで
`X-Content-Type-Options` などの基本的なヘッダを付けます。
キャッシュ指定は入れていません。ファイル名にハッシュを付けていないため、
長いキャッシュを指定すると更新が反映されなくなるからです。

#### 画面にPagesの選択肢が出ない場合

Cloudflare の「Import a repository」はWorkersのフローに入ることがあります
（画面に "Configure your **Worker** project"、Deploy command に
`npx wrangler deploy` と出ていたらそれです）。そのままでは
`Missing entry-point to Worker script or to assets directory` で失敗します。

その画面のまま進めるなら、**Deploy command を `npm run deploy` に変えて**ください。
`package.json` の `deploy` スクリプトが、Pagesプロジェクトを作ってから
Pagesとしてデプロイします（プロジェクトが既にあれば作成は読み飛ばします）。

#### Workers ではなく Pages を使う理由

Cloudflare の「Connect to Git」は、既定だとプロジェクトを Workers の静的アセット
として取り込みます。それでも動きますが、URLがアカウント名を含む
`<プロジェクト名>.<アカウント名>.workers.dev` になります。
Pages なら `<プロジェクト名>.pages.dev` で、アカウント名が入りません。

また Workers 経路では、ビルド中に `npx wrangler deploy` が走って
`node_modules` が作られ、その中の `workerd`（146MiB）が
「1ファイル25MiBまで」の上限に引っかかってデプロイが失敗します
（除外するには `.assetsignore` が要ります）。Pages 経路ではこれが起きません。

SNSに貼ったときのリンクプレビュー（OGP）は `index.html` に絶対URLで書いています。
クローラーはJavaScriptを実行しないため、公開先を変えたときは
`og:url` / `og:image` / `twitter:image` / `canonical` を差し替えてください。
サムネイル画像は `assets/ogp.png`（1200×630）です。
シェア文に添えるURLのほうは実行時に `location` から作るので、差し替え不要です。

Cloudflare Pages は非公開リポジトリでも使えます。
GitHub Pages は無料プランだと公開リポジトリでしか使えないので、
ソースを見せたくない場合はリポジトリを非公開にする手もあります。

### そのほか

Netlify・Vercel でも、リポジトリの内容をそのまま置くだけで公開できます。
GitHub Pages で公開していたときのワークフローは、Cloudflareへ移したので削除しました。
